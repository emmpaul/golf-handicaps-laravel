# Architecture

Monolithe Laravel 13 + Inertia 3 + React 19, PostgreSQL 18, monté selon le squelette Laravel du mainteneur. Chaque décision d'architecture a son ADR sous `docs/adr/` (index dans `docs/adr/README.md`) ; les écarts au squelette sont dans l'ADR 0005.

## Structure (ADR 0001)

- Code métier sous `app/Domain/<Domaine>`, indépendant de HTTP, d'Inertia et des intégrations :
    - `Actions/` : une classe par écriture, méthode `handle()`, qui ouvre sa transaction ;
    - `Queries/` : une classe par lecture complexe ;
    - `Exceptions/` : sous-classes de `App\Domain\DomainException`, avec un message pour la personne qui utilise l'application. Elles sont rendues au même endroit pour toute l'application, dans `bootstrap/app.php` : en visite Inertia, retour arrière avec le flash `toast` `{ type: 'error', message }` ; en requête JSON hors Inertia, 422 `{ "error": message }`.
- Un dossier de domaine naît avec son premier code, jamais vide d'avance.
- Intégrations tierces (IA, Simulator Golf Tour) sous `app/Integrations`, sans dépendance vers `App\Http` ni Inertia ; le domaine ne les appelle pas.
- Contrôleurs minces : Form Request, puis une Action ou une Query, puis la réponse.
- Les frontières sont des règles d'architecture Pest (`tests/Arch/ArchitectureTest.php`, `make arch-test`).

## Données (ADR 0002)

- PostgreSQL partout : local, tests (base `testing`) et CI.
- Chaque modèle de `App\Models` utilise `HasUuids` (UUID v7) ; chaque clé étrangère applicative est un `foreignUuid` avec contrainte. Les tables techniques du framework gardent leurs identifiants.
- Aucune table de comptes. Sessions, cache et files en base, sans Redis. Un worker de file tourne dès le départ : l'import IA et la recherche SGT l'exigent.

## Joueurs et rounds (ADR 0009)

- Domaines `app/Domain/Players` (Actions `AddPlayer`, `RenamePlayer`, `AssignAlias`, `RemoveAlias`, `CreateInitialPlayers` ; normalisation `PlayerName`) et `app/Domain/Rounds` (Actions `CreateRound`, `UpdateRound`, `DeleteRound` ; Queries `RoundList`, `RoundDetail`, `KnownCourses`, `FindDuplicateRound`).
- Tables, toutes en UUID v7 avec leur modèle et leur fabrique :

| Table            | Rôle                                           | Contraintes principales                                                               |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| `players`        | joueurs du groupe                              | unique sur `lower(name)`                                                              |
| `player_aliases` | noms lus sur la carte, en majuscules           | FK en cascade, unique sur `lower(alias)`                                              |
| `rounds`         | parcours, tees, `played_on`, `photo_path`      | index `(played_on, created_at)`                                                       |
| `round_holes`    | par, index et distance de chaque trou du round | uniques `(round_id, hole)` et `(round_id, stroke_index)`, `CHECK`                     |
| `round_players`  | lignes de la carte, dans l'ordre               | FK `players` en `restrict`, uniques `(round_id, player_id)` et `(round_id, position)` |
| `scores`         | brut par joueur et par trou                    | FK composite vers `round_players`, unique `(round_id, player_id, hole)`, `CHECK` 1–15 |

- Contrôles doubles : `App\Domain\Rounds\RoundCardChecks` (serveur) et `resources/js/lib/round-checks.ts` (éditeur, à chaque frappe) donnent les mêmes problèmes avec les mêmes messages. `CreateRound` et `UpdateRound` les rejouent dans leur transaction et lèvent `IncoherentRoundCard` avant toute écriture ; les Form Requests ne valident que la forme. Les `CHECK` de la base sont une seconde ligne.
- Table de cas : `tests/fixtures/round-checks.json`, problèmes attendus écrits à la main, parcourue par `tests/Unit/Rounds/RoundCardChecksTest.php` et `resources/js/lib/round-checks.test.ts`. Un contrôle modifié se change dans les deux codes et dans la table.
- Doublon : `FindDuplicateRound` (parcours et tees sans casse, date, bruts par joueur) est appelé par le contrôleur quand `force` est faux ; il revient à l'éditeur avec le flash `duplicate` sans rien écrire. Ce n'est pas un invariant, donc pas dans l'Action.
- Photos : disque `photos` (`storage/app/photos`, `serve => false`), hors de la racine du disque `local` que sert `storage/{path}`. `photo_path` est relatif à ce disque. `GET /rounds/{round}/photo` (`rounds.photo`) la sert derrière la session ; `DeleteRound` l'efface après le commit.
- Joueurs initiaux : le service `migrate` de `docker-compose.yml` lance `php artisan migrate --force && php artisan golf:initial-players && php artisan golf:recompute-stats && php artisan golf:queue-rating-lookups`. `golf:initial-players` crée les joueurs de `INITIAL_PLAYERS` sur une base sans joueur ; une liste en double la fait sortir en 1, et `web` et `worker` ne démarrent pas.
- Données de développement : chaque seeder étend `Database\Seeders\DemoSeeder`, dont `__invoke()` refuse la production (règle d'architecture). `make fresh` recrée la base avec Gab, Manu et Sean, sans round. `make demo` la recrée avec `DemoDatabaseSeeder` : les mêmes joueurs, le round de référence `IMG_3064` et sa photo (`database/data/img3064.webp`), 24 rounds générés par `CreateRound` avec `fake()->seed(2026)`. `DemoCourseRatingsSeeder` écrit avant les rounds, par la fabrique, une ligne de rating par parcours du jeu (BETHPAGE BLACK / Red et PAYNES VALLEY / Blue « Proposition à confirmer », CALA NOVA / White « Introuvable sur SGT »), pour qu'aucune recherche ne parte ; après les rounds, `DemoConfirmedRatingSeeder` confirme la proposition 71,4 / 144 de Bethpage par `ConfirmCourseRatingProposal`, qui recalcule. Le jeu refuse une base qui a déjà un joueur ou un round.

## Index et ratings (ADR 0010, ADR 0012)

- Calcul pur : `App\Domain\Handicaps\Whs` (score ajusté, différentiel, index, handicap de jeu et de parcours) et `NetRanking` (rang net de compétition), ports un pour un de `handicap.ts` et `strokes.ts` de Next, sur des valeurs `final readonly` (`CourseRating`, `RatedCourse`, `RoundDifferential`, `HandicapIndex`, `NetEntry`, `RankedNet`). Une règle d'architecture leur interdit `Illuminate` et `App\Models` ; leurs tests reprennent les valeurs des tests Next.
- Dixièmes entiers : différentiels, index et ratings sont des entiers en dixièmes (`differential_t`, `index_before_t`, `index_after_t`, `rating_t`). Chaque division flottante est suivie de `(int) floor($x + 0.5)`, l'arrondi de Next. Le front formate (`formatTenths(174)` → « 17,4 »).
- Tables, en UUID v7 avec leur modèle et leur fabrique :

| Table                | Rôle                                                                                                                                                                                                                     | Contraintes principales                                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `player_round_stats` | brut, ajusté, différentiel, index d'avant et d'après, `counts_in_current`, sans timestamps                                                                                                                               | FK composite `(round_id, player_id)` vers `round_players` en cascade, unique `(round_id, player_id)`, `CHECK` index ≤ 540                                                                                                         |
| `course_ratings`     | une ligne par parcours et tees : rating et slope confirmés (facultatifs) et leur `source` (`sgt`, `manual`), statut de la recherche, parcours SGT retenu, `candidates` et `tees_read` en `jsonb`, `proposed_tee`, `note` | unique sur `(lower(trim(course_name)), lower(trim(tees)))`, `CHECK` `rating_t` 400–900 et `slope` 55–155, `CHECK` du statut et de la source, `rating_t`, `slope` et `source` nuls ensemble, `confirmed` seulement avec une rating |

- Recalcul : `App\Domain\Handicaps\Actions\RecomputePlayerStats` rejoue l'historique complet de chaque joueur touché (date de jeu, puis `created_at`, puis `id`), dans la transaction de l'écriture et après ses contrôles. Elle verrouille les joueurs par `lockForUpdate()` dans l'ordre des `id`, puis supprime et réécrit leurs lignes. Appelée par `CreateRound`, `UpdateRound` (joueurs d'avant et d'après la correction), `DeleteRound`, `SaveCourseRating`, `RemoveCourseRating`, `ConfirmCourseRatingProposal` et `ChooseCourseRatingTee` (joueurs qui ont un round sur la paire). Sans rating confirmée (`rating_t` nul ou ligne absente), le calcul prend le par du round et le slope 113.
- Ratings : domaine `app/Domain/Courses` (Actions `SaveCourseRating`, `RemoveCourseRating`, `QueueCourseRatingLookup`, `StartCourseRatingLookup`, `FinishCourseRatingLookup`, `ConfirmCourseRatingProposal`, `ChooseCourseRatingTee`, `ChooseSgtCandidate`, `RelaunchCourseRatingLookup` ; Queries `CourseOverview`, `CourseRounds` ; conversion `RatingInput` de « 71,4 » en 714 ; enum `CourseRatingStatus`). Une paire se compare toujours en SQL avec `lower(trim(...))`, la même expression que l'index unique et que `KnownCourses`. La saisie fait un `insert … on conflict … do update` qui pose `confirmed` et `source = manual` sans toucher à la recherche ; une paire sans round lève `UnknownCourse`, un retrait sans rating `CourseHasNoRating`. Le retrait efface la rating et garde la recherche : la ligne revient à la proposition, aux tees lus, aux candidats ou à « Saisie manuelle ». Routes `GET /courses`, `PUT` et `DELETE /courses/rating`.
- Statuts de la recherche (`CourseRatingStatus`, schéma de Next gardé pour l'import) : `pending` « Recherche en cours », `proposed` « Proposition à confirmer », `choose_course` « Parcours SGT à choisir », `choose_tee` « Tee à choisir », `manual` « Saisie manuelle », `not_found` « Introuvable sur SGT », `failed` « Recherche échouée », `confirmed` « Confirmé ». La recherche n'écrit jamais `rating_t`, `slope` ni `source` : une valeur ne compte qu'après une confirmation.
- Mise en file : `QueueCourseRatingLookup` insère une ligne `pending` par paire nouvelle (`on conflict do nothing`) et pousse `App\Jobs\LookUpCourseRating` après le commit. `CreateRound` et `UpdateRound` l'appellent dans leur transaction, l'import passe par `CreateRound`. `golf:queue-rating-lookups` le fait pour chaque paire des rounds sans ligne, du round le plus ancien au plus récent, et affiche « N recherches de rating mises en file. » ; le service `migrate` la lance après `golf:recompute-stats`. Le web et `migrate` ne joignent jamais SGT.
- Recherche par le worker : `LookUpCourseRating` (2 essais à 30 s, 120 s au plus) passe la ligne par `StartCourseRatingLookup` (rien si elle n'est plus `pending`), lit `SGT_LOOKUP`, le par du dernier round de la paire, la liste SGT, la correspondance, la clé et le budget, l'image de la carte et sa lecture par l'IA (usage compté dans `ai_usage` aussitôt), puis écrit l'issue par `FinishCourseRatingLookup` sous verrou, seulement si la ligne est encore `pending`. Deux échecs passagers (SGT injoignable, erreur de l'IA) : `failed()` écrit « Recherche échouée », « SGT injoignable ».
- Correspondance pure : `App\Domain\Courses\Sgt` (`SgtCourseMatcher` : normalisation des noms, correspondance au même par, au plus 10 candidats, tees sans distance ; `SgtLinks` : adresse de la carte SGT et lien The Course View ; valeurs `SgtCourse`, `SgtTee`, `SgtCard`, `SgtMatch`). Une règle d'architecture lui interdit `Illuminate` et `App\Models`, comme à `Whs`.
- Intégration Simulator Golf Tour : `app/Integrations/Sgt` (`SgtClient` : liste des parcours gardée 24 h dans le cache Laravel, image d'une carte, `User-Agent` qui nomme le dépôt, 20 s par requête dont 10 de connexion ; `SgtCoursesPage` : lecture du bloc `courses-data` de la page ; `SgtUnavailable` pour toute erreur). La lecture de la carte est `App\Integrations\Ai\SgtScorecardReader` (`SgtCardReading`), bornée à `golf.ai.rating_max_input_tokens` 2 000 et `rating_max_output_tokens` 1 500 ; `AiBudget::canSpend()` reçoit le coût maximal de cette lecture. Seul `App\Jobs` utilise `App\Integrations\Sgt`, et `App\Domain` ne l'utilise pas (règles d'architecture).
- Actions de la page Parcours : `CourseRatingLookupController`, `POST /courses/ratings/{courseRating}/confirmation`, `/tee`, `/candidate` et `/lookup` (« Confirmer », « Retenir », « Choisir », « Relancer la recherche »). Chaque action verrouille la ligne ; confirmer et retenir posent la rating du tee lu avec `source = sgt` et recalculent, choisir et relancer remettent la ligne `pending` et poussent le job après le commit, la rating confirmée gardée. `CourseOverview` ajoute à chaque paire l'état de sa ligne, la proposition, les tees lus, les candidats et les liens ; la page reçoit `lookupPending` et se relit toutes les 2 s tant qu'une ligne cherche.
- `SGT_LOOKUP` (`golf.sgt.lookup`, `on` par défaut) : `off` fait finir chaque recherche en « Saisie manuelle », « Recherche SGT désactivée », sans requête ; une autre valeur fait refuser le démarrage par `AppServiceProvider::ensureSgtConfiguration()`.
- Faux des tests : `phpunit.xml` pose `SGT_LOOKUP=off` et `CACHE_STORE=array`, donc chaque round écrit par un test (file `sync`) finit sa recherche sans réseau. Un test de la recherche active `golf.sgt.lookup`, sert `tests/fixtures/sgt/` (`courses.html`, `scorecard_30.jpg`) par `Http::fake` et fournit la lecture facturée (`billedSgtReading()` de `tests/Pest.php`). `tests/Pest.php` ajoute `SgtScorecardReader::fake()->preventStrayPrompts()` au garde-fou global.
- Lectures : le handicap de jeu et le net ne sont pas stockés. `RoundLeaderboard` les calcule depuis `index_before_t` et la rating courante du round ; `RoundList` en tire les gagnants nets ; `PlayerOverview` lit l'index d'après le dernier round joué et le marque provisoire sous 3 rounds.
- Accueil, Handicaps et Coups : `PlayerStandings` rend l'index, l'écart du dernier round joué et la marque provisoire de chaque joueur (sous-requête partagée avec `PlayerOverview`) ; `PlayerHandicapHistory` rend les rounds d'un joueur, du plus récent au plus ancien, avec différentiel, index d'après et `counts_in_current` ; `PendingImports` compte les imports prêts à vérifier sans round et rend le plus récent ; `RoundList::get(1)` rend le dernier round joué ; `CourseOverview` porte les index de trou du round le plus récent de chaque paire. Les coups d'une partie se calculent dans le navigateur (`resources/js/lib/strokes.ts`, port de `strokes.ts` de Next), sans requête : le jeu de cas `tests/fixtures/course-handicap.json` est lu à la fois par Pest (`Whs`) et par Vitest (`lib/strokes.ts`).
- `golf:recompute-stats` : recalcule tous les joueurs qui ont un round, dans une transaction, et affiche « N joueurs recalculés. » (code 0, même sur une base sans round). Idempotente. Le service `migrate` la lance à chaque déploiement après `golf:initial-players` : le staging, une restauration de dump et l'import obtiennent leur historique sans étape à la main.

## Import des cartes (ADR 0011)

- Domaines `app/Domain/Imports` (Actions `CreateImport`, `StartReading`, `MarkImportReady`, `FailImport`, `SaveImportCorrection`, `SaveImportedRound`, `RetryImportReading`, `DeleteImport` ; Query `ImportList` ; valeurs `ScorecardDraft`, `SimulatorDate`, `ImportCorrection`, `ImportEditorState`, `WebpPhoto`) et `app/Domain/AiUsage` (`AiBudget`, `AiPricing`). La reconnaissance des noms lus est `App\Domain\Players\PlayerNameMatcher`.
- Tables, en UUID v7 avec leur modèle et leur fabrique :

| Table      | Rôle                                                                                                                                                    | Contraintes principales                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `imports`  | photo envoyée, statut, brouillon lu (`draft`), correction de l'autosave, raison d'un échec, round créé, clé d'envoi tirée sur l'appareil (`upload_key`) | `CHECK` du statut, `CHECK` d'un brouillon présent quand `ready`, FK `round_id` unique vers `rounds` en cascade, index `created_at`, `upload_key` `uuid` nullable et unique |
| `ai_usage` | un appel facturé : mois du budget (`YYYY-MM`), modèle, tokens d'entrée et de sortie, coût                                                               | `CHECK` des trois compteurs ≥ 0, `cost_micro_usd` en micro-dollars entiers, index `month`                                                                                  |

- Envoi d'une photo (`POST /imports`, ADR 0016) : `StoreImportRequest` exige `photo` et `upload_key` (UUID tiré sur l'appareil). `CreateImport::handle($photo, $uploadKey)` rend l'import existant d'une clé déjà reçue sans décoder la photo ni rien écrire ; sur une violation de l'unique (deux envois simultanés de la même clé), il efface la photo qu'il vient d'écrire et rend l'import gagnant. `ImportController::store` revient en arrière avec le toast pour une visite Inertia, et répond à une requête JSON `201 { "id" }`, ou `200 { "id" }` pour une clé déjà reçue (`wasRecentlyCreated` faux). Un refus métier y est un `422 { "error" }`, une erreur de validation le `422 { "message", "errors" }` de Laravel, une requête sans session `401 { "error": "Session requise" }`. Les imports d'avant ce changement, et ceux de `DemoImportsSeeder`, n'ont pas de clé.
- Statuts (`ImportStatus`) : `queued` « En attente », `reading` « Lecture en cours », `ready` « Prêt à vérifier », `failed` « Échec » avec sa raison dans `failure` (`ReadingFailure`). Un import relié à un round est enregistré : sa page redirige vers le round, il ne se corrige, ne se relance ni ne se supprime plus. Supprimer le round supprime l'import (cascade).
- Job : `CreateImport` et `RetryImportReading` poussent `App\Jobs\ReadScorecardImport` après le commit. Le job passe l'import à `reading` sous verrou (rien si l'import a disparu ou n'attend plus), refuse sans clé ou sans budget, appelle l'IA, compte l'usage dans `ai_usage` avant toute décision, puis écrit `ready` avec le brouillon ou `failed` « Lecture IA indisponible ». Deux essais (`$tries = 2`) pour les erreurs passagères du SDK ; `failed()` écrit le même échec.
- Budget : `AiBudget::canSpend($now)` vrai tant que le cumul du mois plus le coût de l'appel le plus cher (`max_input_tokens` 6 000, `max_output_tokens` 4 000) tient sous `AI_MONTHLY_BUDGET_USD`. Mois dans le fuseau `AI_BUDGET_TIME_ZONE`, prix par token dans `config/golf.php` (`golf.ai.prices`). Vérifié avant chaque appel et à la demande de relance. `AppServiceProvider::boot()` refuse de démarrer quand `AI_MODEL` n'a pas de tarif ou que le fuseau est inconnu.
- Intégration hors du domaine : `app/Integrations/Ai` (`ScorecardPhotoReader`, agent du Laravel AI SDK en sortie structurée ; `ScorecardImage`, JPEG de 1568 px envoyé à l'IA ; `ReadingResult`). Seul `App\Jobs` l'utilise ; `App\Domain` n'utilise ni `App\Integrations` ni `Laravel\Ai` (règles d'architecture). Le domaine reçoit la carte lue en tableau et la contrôle par `ScorecardDraft::fromArray()`.
- Faux obligatoires des tests : `phpunit.xml` vide `ANTHROPIC_API_KEY` ; `tests/Pest.php` appelle avant chaque test qui démarre l'application `ScorecardPhotoReader::fake()->preventStrayPrompts()` et `Http::preventStrayRequests()`. Un test qui lit une carte pose `config(['ai.providers.anthropic.key' => 'test-key'])` et fournit la réponse, usage compris (`StructuredTextResponse` avec un `TextUsage`). Un prompt sans réponse fournie lève.
- Photos des imports : disque `photos`, sous `imports/<uuid>.webp`, en WebP de 3000 px au plus sans EXIF ni XMP (`WebpPhoto`, Intervention sur Imagick). `GET /imports/{import}/photo` (`imports.photo`) la sert derrière la session. Le round créé depuis un import garde le même `photo_path` ; `DeleteRound` efface le fichier, `DeleteImport` aussi pour un import pas enregistré, toujours après le commit.
- Correction : l'éditeur des rounds envoie son état par `PUT /imports/{import}/correction` une seconde après la dernière modification (`autosave.ts`), gardé dans `imports.correction` (`{ version: 1, card }`) ; `ImportEditorState` rouvre la correction, sinon le brouillon, sinon un écran vide. L'enregistrement (`POST /imports/{import}/round`) passe par `CreateRound`, les contrôles des totaux lus compris, puis apprend en alias les noms lus qui ne désignaient pas exactement leur joueur.
- Données de développement : `make demo` ajoute par `DemoImportsSeeder` un import « Prêt à vérifier » de la carte de référence avec une ligne lue « JULIEN », un « Échec » « Budget IA du mois atteint », un « En attente » sans job, chacun avec sa photo, et 3 lignes d'`ai_usage` du mois courant. Aucun appel à l'IA.

## Import de la base Next (ADR 0014)

- Commande `golf:import-sqlite {db} {--uploads=} {--force} {--dry-run}` (`App\Console\Commands\ImportSqliteCommand`), lancée une fois au cutover. Elle lit les options, pose la question de `--force` (non par défaut, non sans terminal), appelle `App\Domain\LegacyImport\Actions\ImportLegacyDatabase` et affiche le rapport (`ImportReport`) ou l'erreur. Elle sort en 0 sur un import ou un essai à blanc réussis, en 1 sinon. Procédure de bascule : `docs/deployment.md`, « Bascule depuis Next ».
- Domaine réservé : seul `ImportSqliteCommand` utilise `App\Domain\LegacyImport`, qui n'utilise ni `App\Http` ni la façade `Log` (règles d'architecture). Ses refus sont des `LegacyImportFailed` (message pour l'opérateur et liste de détails), hors de `App\Domain\DomainException` : aucune requête HTTP ne les rend, et aucune ligne de la base Next ne part dans le journal.
- Lecture : connexion `legacy` déclarée à la volée sur le fichier, en lecture seule (`Pdo\Sqlite::OPEN_READONLY`). `LegacySchema` vérifie les tables et colonnes du niveau Drizzle `0004` avant toute écriture, colonnes en plus tolérées.
- Écriture : insertions directes par `DB::table()`, sans les Actions des domaines, dans une seule transaction avec la copie des photos (une photo écrite est effacée si la transaction échoue). Les contraintes de PostgreSQL restent la garde ; une ligne refusée fait échouer l'import en nommant la table et la clé SQLite. Seule normalisation : une distance hors de 1 à 999 devient vide.
- Identifiants : `IdMap` garde en mémoire la correspondance `id` SQLite → UUID. Pour chaque table à `id`, les UUID v7 générés sont triés puis attribués dans l'ordre des `id` SQLite : `order by created_at, id` rend l'ordre de Next malgré des dates tronquées à la seconde et deux joueurs créés dans la même milliseconde (couleur de joueur, historique d'index).
- Photos : `LegacyPhotos` copie chaque chemin `uploads/<nom>` une fois vers `imports/<nom>.webp` du disque `photos`, chemin partagé par le round et l'import, et convertit en WebP ce qui ne l'est pas (`WebpPhoto`).
- Statistiques : `player_round_stats` n'est pas copiée. `RecomputePlayerStats` la recalcule dans la transaction, puis `StatsComparison` la compare colonne par colonne à celle de Next ; un écart annule l'import et liste chaque différence.
- Après le commit : effacement des photos des lignes vidées par `--force`, et `LookUpCourseRating` mis en file pour chaque rating importée `pending`. `--dry-run` fait tout puis annule, sans écrire de photo ni mettre de job en file.
- Tests : `tests/Support/LegacySqlite/LegacySqliteFixture` construit une base SQLite à chaque test depuis les migrations Drizzle de Next copiées sous `tests/fixtures/legacy-sqlite/drizzle/`, avec des valeurs littérales. Aucune base réelle n'est versionnée.

## Heures et fuseau (ADR 0004)

- `app.timezone` reste `UTC`. Chaque instant envoyé à une page passe par `App\Domain\LocalTime`, qui le convertit vers `app.display_timezone` (`America/Montreal`).
- Les bornes d'un jour se calculent en heure locale (`LocalTime::startOfDay`) puis se ramènent en UTC.

## Accès (ADR 0007)

- Code d'accès partagé (`APP_PASSCODE`, lu par `config('app.passcode')`) et session, sans comptes ni rôles.
- Fermé par défaut : `RequirePasscode` est dans le groupe `web` (`bootstrap/app.php`). Une route ajoutée à `routes/web.php` exige la session sans rien déclarer.
- Exceptions : `GET` et `POST /login` s'en retirent par `withoutMiddleware()`. `GET /api/version` (groupe `api`), `/up` et les fichiers statiques de `public/` sont hors du groupe `web`. `tests/Feature/ProtectedRoutesTest.php` compare la liste des routes ouvertes à une liste littérale : ouvrir une route demande de la mettre à jour.
- Adresse inconnue : la route de repli de `routes/web.php` répond 404 avec session et redirige vers `/login` sans session. Sous `api/`, 404 dans tous les cas.
- Refus : une lecture de page ou une visite Inertia est redirigée vers `/login` (303 pour une visite `PUT`/`PATCH`/`DELETE`, par le middleware global `EnsureGetOnRedirect` d'Inertia), toute autre requête reçoit 401 `{ "error": "Session requise" }`. `RequirePasscode` tourne avant `PreventRequestForgery` : un jeton CSRF périmé donne 401, pas 419.
- Empreinte : `App\Support\Passcode::fingerprint()` est le HMAC SHA-256 du code, avec `APP_KEY` pour clé. La connexion (`LoginController::store`) régénère l'identifiant de session et y range cette empreinte sous `access.passcode`, jamais le code. Changer `APP_PASSCODE` ou `APP_KEY` ferme toutes les sessions.
- Sessions en base, chiffrées (`encrypt` à `true` par défaut), 90 jours glissants (`SESSION_LIFETIME=129600` minutes). `POST /logout` ferme la session de ce navigateur seulement.
- Limiteur : 10 essais par minute et par IP sur `POST /login` (`LoginRequest::authenticate`), réussites comprises.
- Sans `APP_PASSCODE`, `EnsurePasscodeConfigured`, premier contrôle de la pile globale, fait répondre 500 à toute requête HTTP, `/up` compris, avec un message qui nomme la variable. Les commandes artisan tournent sans elle.
- En-têtes : `AddSecurityHeaders`, en tête de la pile globale, juste avant `EnsurePasscodeConfigured`, pose `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` et `Content-Security-Policy: frame-ancestors 'none'` sur toute réponse, erreurs (le 500 d'un code manquant aussi), redirections, `/up` et JSON compris. Une réponse qui pose sa propre `Content-Security-Policy` la garde.
- Mandataires : `config/trustedproxy.php` lit `TRUSTED_PROXIES` (adresses ou plages CIDR séparées par des virgules) pour le `TrustProxies` de Laravel. Vide, aucun mandataire n'est de confiance ; `*` et `**` sont retirés. Le limiteur voit ainsi l'IP du client derrière le proxy de Dokploy.

## Déploiement (ADR 0008, ADR 0015)

- Une seule image de production (`Dockerfile`, FrankenPHP, PHP 8.5), sans secret, sous l'utilisateur `app`. La commande lancée choisit le rôle : web (`php artisan octane:frankenphp`, port 8080, `docker/Caddyfile`), worker (`queue:work`) ou migrations. `docker/entrypoint.sh` construit les caches Laravel (`php artisan optimize`) au démarrage, une fois l'environnement connu.
- Web en mode worker (ADR 0015) : Laravel Octane fait tourner FrankenPHP en workers qui gardent l'application chargée (`--workers=auto`), chacun relancé après 500 requêtes (`--max-requests=500`). `docker/Caddyfile` déclare le worker (`public/frankenphp-worker.php`, posé au build), garde `admin off`, `auto_https off`, la compression et l'en-tête `immutable` de `/build/*`, et sert les fichiers de `public/` (`favicon.ico`, `robots.txt`) sans PHP. Le worker de file et `migrate` restent des commandes artisan ordinaires.
- État entre requêtes : Octane clone l'application à chaque requête et lance les écouteurs `RequestReceived` de `config/octane.php` (session, authentification, témoins en file, configuration). Le code ne garde aucun état de requête en propriété statique ni en `singleton()` : ce qui dépend de la requête passe par `scoped()` (seul cas : `QueryClock`), par la requête ou par la liste `flush` de `config/octane.php`. `tests/Feature/WorkerRequestIsolationTest.php` fait passer deux navigateurs dans un même worker d'Octane : ni session, ni flash, ni erreur de validation ne passe de l'un à l'autre, et un code d'accès changé ferme les sessions ouvertes.
- La CI construit l'image, lance la stack (`make image`, `make image-smoke`) et publie sur `ghcr.io/emmpaul/golf-handicaps-laravel` l'image qu'elle a testée : `:main` et `:<sha>` depuis `main`, `:vX.Y.Z`, `:latest` et `:<sha>` depuis un tag dont `version.txt` porte la version (`make image-tags`).
- Stack `docker-compose.yml` pour Dokploy : `pgsql`, `migrate` (une fois par déploiement), `web` et `worker` (après la réussite de `migrate`), `backup`. Volumes nommés `pgdata`, `storage` (monté sur `storage/app` pour `web` et `worker`) et `backups`. Aucun port publié.
- Santé : `web` est sain quand `/up` répond 200. `worker` l'est tant que `App\Support\WorkerHeartbeat` a écrit `/tmp/worker-heartbeat` il y a moins de 300 s ; le battement suit `Queue::looping`, `JobProcessed` et `JobFailed`, donc seul `queue:work` l'écrit. `backup` l'est tant qu'un dump réussi a moins de 26 h.
- Sauvegardes : `pg_dump -Fc` au démarrage puis toutes les 24 h, gardées 14 jours. La restauration est dans `docs/deployment.md`.
- TLS chez Traefik (Dokploy). `AddSecurityHeaders` pose `Strict-Transport-Security: max-age=31536000` sur toute réponse servie en HTTPS, d'après `isSecure()` lu après les mandataires de confiance. Le témoin de session est `Secure` par défaut quand `APP_ENV=production` (`config/session.php`). `TRUSTED_PROXIES` vaut en production le sous-réseau du proxy de Dokploy, jamais `*`.
- L'image installe `imagick` (conversion des photos en WebP) et `docker/php/uploads.ini` (envoi jusqu'à 20 Mo). `ANTHROPIC_API_KEY`, `AI_MODEL`, `AI_MONTHLY_BUDGET_USD` et `AI_BUDGET_TIME_ZONE` arrivent par l'environnement de `migrate`, `web` et `worker`, jamais par l'image.
- Journaux sur la sortie d'erreur du conteneur (`LOG_CHANNEL=stderr`), gardés et tournés par Docker.
- Procédures (installation, version, santé, sauvegarde, restauration, retour arrière, bascule depuis Next, fermeture des sessions) : `docs/deployment.md`.

## Frontend (ADR 0006, ADR 0016)

- Inertia 3 + React 19, sans rendu serveur. Pages sous `resources/js/pages`, sans fichier de test : le plugin Vite d'Inertia emballe tout `.tsx` de ce dossier comme page, les tests de page vont sous `resources/js/tests/pages` ; composants sous `resources/js/components`, primitives base-ui possédées par le projet sous `resources/js/components/ui`. Thème, tokens et règles d'interface : `DESIGN.md`.
- `resources/js/layouts/app-layout.tsx` est le layout par défaut de chaque page (option `layout` de `createInertiaApp` dans `app.tsx`) : navigation (`AppNav`), `main`, ligne de version (`AppVersion`) en dernier enfant de `main`, puis `Toaster`.
- Données partagées par `HandleInertiaRequests::share()` : `name` et `app: { version, commit }`, typées dans `resources/js/types/global.d.ts`. `App\Support\AppBuild` lit la version et valide le commit (sha de 40 caractères hexadécimaux minuscules, sinon `null`) ; `VersionController` passe par la même classe.
- Messages éphémères par le flash Inertia : clé `toast`, `{ type: 'error' | 'success', message }`, typée par `flashDataType`. Le serveur l'émet par `Inertia::flash('toast', …)` ; le layout l'écoute par `router.on('flash', …)` et `showFlashToast` (`resources/js/lib/flash-toast.ts`) l'affiche. Le rendu de `DomainException` l'émet en `error`, les contrôleurs de rounds en `success` (« Round enregistré. », « Round supprimé. »).
- Routes : `/` sert `home` par `HomeController`, `/handicaps` sert `handicaps/index` par `HandicapController` (joueur choisi dans `?joueur=`, le premier par nom à défaut) et `/strokes` sert `strokes/index` par `StrokesController`, sous les noms `home`, `handicaps.index` et `strokes.index`. `/rounds` et `/players` ont leurs pages (section « Joueurs et rounds »), `/import` et `/imports/{import}` les leurs (section « Import des cartes »). Il n'y a plus de page de repli « Section à venir » : une sous-adresse inconnue répond 404. La navigation lit les adresses dans les fonctions Wayfinder.
- Section courante : `inSection` et `SECTION_PREFIXES` (`resources/js/lib/sections.ts`) rattachent `/imports/…` à Importer et `/courses/…` à Rounds.
- `public/manifest.webmanifest`, `public/icons/` et `public/apple-touch-icon.png` sont statiques, servis par le serveur web sans session. `php artisan app:icons` régénère les PNG.
- Service worker (ADR 0016) : `public/sw.js`, script classique écrit à la main, sans build, servi par Caddy à la racine en `text/javascript` avec `Cache-Control: no-cache`, sans session. `app.tsx` l'enregistre seulement avec les assets compilés (`import.meta.env.PROD`), puis, au premier chargement en ligne avec une session, lui envoie `{ type: 'cache-import', version }` pour garder `/import` sous ses deux formes et précharge le morceau de la page Importer par `import()`. Il fait `skipWaiting()` et `clients.claim()`.
- Caches du service worker : `assets` (`/build/*` « cache d'abord », 300 entrées au plus), `pages` (« réseau d'abord », 100 entrées au plus), `offline` (`/offline.html` seul, gardé à l'installation, jamais effacé à la déconnexion). Une page est gardée sur un `GET` de même origine en `200` non redirigé, hors `/build/`, `/login`, `/api/`, `/up`, photos des rounds et des imports, fichiers statiques de `public/` et rechargements partiels d'Inertia ; sa clé est l'adresse nue pour un document, l'adresse suivie de `?__sw=inertia` pour une visite Inertia ; la copie porte `X-Offline-Stored-At`. Hors ligne, une copie servie porte `X-Offline: hit` et déclenche le message `{ type: 'served-from-cache', url, storedAt }` ; sans copie, `/offline.html` pour un document et `503` `X-Offline: miss` pour une visite Inertia. `pages` est vidé sur la réponse de `POST /logout`, une réponse qui mène à `/login` (redirection ou `409` `X-Inertia-Location`), un `401` « Session requise » et un `200` de `GET /login`. Les fonctions pures du fichier sont testées dans `resources/js/tests/service-worker.test.ts` ; `public/offline.html`, autonome (HTML et CSS en ligne aux valeurs des tokens), dans `tests/Feature/OfflinePageTest.php`.
- Hors ligne dans l'application : `OfflineBanner` (dans `app-layout.tsx`) affiche « Hors ligne », suivi de « · page du <jour> à <heure> » (`formatStoredAt`) quand la page courante vient d'une copie ; `resources/js/lib/offline.ts` écoute le routeur Inertia et montre « Page indisponible hors ligne. » sur un `503` `X-Offline: miss`, « Hors ligne : rien n'a été envoyé. » sur une visite autre que `GET` finie en `networkError`.
- File des photos (ADR 0016) : `resources/js/lib/photo-queue.ts` garde chaque photo préparée dans IndexedDB (base `golf-offline`, magasin `photos`, `{ key, blob, takenAt }` indexé par `takenAt`) et l'envoie par `fetch` à `POST /imports` en `FormData` (`photo`, `upload_key`), avec `Accept: application/json`, `X-Requested-With` et `X-XSRF-TOKEN`, sans `X-Inertia`. API : `enqueue`, `list`, `remove`, `flush`, `subscribe`, `sendingKey`. `flush()` envoie une photo à la fois, de la plus ancienne à la plus récente, sous le verrou `navigator.locks` `golf-offline-photos` (une chaîne de promesses à défaut) ; `201`/`200` efface la photo, `422`/`413` l'efface et rend le refus, `401` arrête et demande `/login`, `419` refait un essai après un `GET` de la page, toute autre réponse, une erreur réseau ou 60 s sans réponse arrêtent et gardent la photo. `BroadcastChannel` `golf-offline-photos` prévient les autres onglets. `app.tsx` lance `flush()` à l'ouverture, sur `online` et au retour au premier plan. `navigator.storage.persist()` est demandé à la première mise en file. La déconnexion ne vide pas la file. Les tests chargent `fake-indexeddb` par `resources/js/tests/indexeddb.ts`.

## Outillage (ADR 0003)

- Chaque changement passe par OpenSpec, en TDD.
- Le Makefile est l'interface unique, en local et en CI : `make` liste les cibles, `make check` lance tous les contrôles.
- Version tenue à la main dans `version.txt`, changements notés dans `CHANGELOG.md` par chaque pull request de code (ADR 0005).
